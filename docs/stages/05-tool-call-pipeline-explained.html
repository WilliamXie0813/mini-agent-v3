mini-agent-v3 · 阶段 5 · 三段式工具调用与拦截

工具调用 Pipeline 图解

阶段 5 最重要的不是多了一个 hook，而是把「准备」「执行」「收尾」拆成三个边界。这样权限判断能停在副作用之前，update 与最终结果也不会互相穿插。

1

权限问题必须发生在副作用之前

阶段只负责不会做
prepare找工具、schema 校验、before hook、block 判定不调用 tool.execute
execute执行工具、收集 onUpdate、捕获工具 throw不生成历史消息
finalize归一化 result、duration、ToolResultMessage不再调用工具或 hook
先认识几个词（第一次看再展开）
before hook
执行前的权限检查函数；它可以放行，也可以直接拒绝整个调用。
block 判定
hook 拒绝之后的状态——这次调用不会跑真正的工具代码，但仍要走完完整生命周期。
prepared data
prepare 阶段产出的、还没有执行任何副作用的中间结果；只有它存在，「执行前还能反悔」才成立。
onUpdate
工具执行过程中用来汇报进度的回调，每调用一次就对应一次 tool_execution_update 事件。
duration / immediate error
duration 是 finalize 阶段统一补上的耗时统计；immediate error 指 prepare 阶段就已经确定失败、根本不会进入 execute 的那种错误（权限拒绝、参数非法、hook 抛错都算）。
terminate
某个工具调用是否要求「这就是这一轮的最后一步，不用再问模型了」。

设想：如果把权限判断写在 execute 内部——判断「允许」之前，bash 工具已经把 rm -rf /tmp/project 跑完了。等 hook 真正返回「拒绝」时，文件已经删掉，拒绝已经来不及生效。

关键判断

如果权限 hook 与 execute 混在一起，唯一能询问用户的时刻就是「工具已经开始运行」。三段式让 prepare 返回一个还没有副作用的 prepared data。

tool_execution_start
  → prepareToolCall()
      → validateJsonSchema()
      → beforeToolCall()
  → executePreparedToolCall()
      → tool.execute(onUpdate)
  → finalizeToolCall()
  → tool_execution_end
  → message_start/end(toolResult)

为什么还要 finalize

blocked / invalid / hook error 都不会进入 execute，但仍然会 finalize，并产生平衡的 end 与 toolResult message——没有这一步，模型永远等不到「为什么失败」的答案。

			为什么 late update 被丢弃
			
late update 被忽略，因为 acceptingUpdates 在工具 promise settle 时已经变成 false——允许它继续写进去，UI 就可能先看到「工具已结束」又看到「旧进度」，时间线会倒流。

			额外规则

6
四个回测问题

	

		

			
1. 为什么 prepare 与 execute 必须分开？

			
			
权限等待必须发生在副作用之前。prepare 返回纯数据，只有 allow 后才进入 execute。

		

		

			
2. 为什么 block 要回喂模型？

			
			
拒绝原因是模型能修的错误；toolResult 让模型换方案，throw 只会让整个 run 失败。

		

		

			
3. 为什么 update 要先于 end settle？

			
			
否则 UI 会先看到工具结束，随后又收到旧进度，事件时间线倒流。

		

		

			
4. 为什么 terminate 按 batch 聚合？

			
			
assistant 已一次性提交整个调用序列；提前 break 会让后续 toolCall 没有配对结果。
