MINI-AGENT / STAGE 09 / DURABLE HISTORY

让历史活过进程

工具正在改文件时进程被杀，重启后你怎么知道文件改了没有？

如果没有保存结果，可能是“还没执行”，也可能是“已经改完，只是来不及记”。这页先让你遇到这个问题，再一步步看日志能证明什么、不能证明什么。

01 / 先试几个直觉方案：哪里会出事？

直觉方案崩溃时会怎样因此需要什么
只把对话放在内存一退出，输入、回复和工具执行线索全丢了。把事实写进磁盘日志。
每次覆盖 session.json写到一半崩溃，可能连旧历史都损坏。只在末尾追加，完整旧记录不动。
工具做完再记“开始执行”文件已改，记录却没写；看上去像从未执行。执行前先留下“接下来可能动手”的记录。
没结果就全部重跑可能把文件再改一次，把命令再执行一次。先区分哪些工具允许重跑。

关键不是“把所有步骤存下来就好了”，而是：先保存证据，再跨过执行边界；重启后只做证据允许的事。

02 / 两张收据，回答两个不同的问题

intent：动手前的记录

大白话：“参数和权限已检查，我接下来可能执行这个工具。”必须先保存它，才能真正动手。它不证明工具已经执行，更不证明执行成功。

outcome：执行结果的记录

大白话：“这次执行返回了什么，是成功还是报错。”保存了它，重启后就能沿用这个结果，不需要再次执行工具。

检查参数和权限 → 保存 intent → 执行工具 → 保存 outcome

“保存”不是只写进内存。这里写入日志后还要等待 fsync，即要求系统把写入同步到磁盘。完成这一步，才称为 durable（已持久化）。日志 journal 就是这本逐条追加的记录簿。

如果停在 intent 和 outcome 之间，我们只知道“可能动过手”。这时看工具作者的 replay（重跑策略）声明：

safe：作者允许再执行一次

例如 read 读取文件。当前工具仍声明 safe、且声明与日志中一致时才重跑。但文件可能已经变了，因此第二次读出的内容不一定相同。

unsafe：不能冒险自动再执行

例如 edit 改文件、bash 跑命令。不知道第一次是否完成，就不再动手；保留已有输出，并明确报告中断。未声明策略时也按 unsafe 处理。

safe 不是“只执行一次”的保证。第一次可能执行了，恢复时又执行一次；所谓 exactly-once，指副作用恰好发生一次，这份本地日志不能对外部工具作出这个承诺。

03 / 先猜，再看这一步留下什么

每步先回答一个小问题，再点“揭示答案与变化”。优先看本步变化；完整日志和模型历史在折叠区，需要时再展开。这里不执行真实文件 I/O、fsync、模型请求或工具。

  1. safe：有 intent、无 outcome，且允许重跑。
  2. unsafe：同样没有 outcome，换成不能冒险重跑的工具。
  3. outcome：如果崩溃晚一点，结果已经保存，还用重跑吗？
  4. branch：理解恢复后，再看同一份日志如何保留两条对话。
  5. dedupe：换分支或重启后，重复请求会不会再执行？
  6. barrier：最后把一个工具推广到并行的一批工具。

前三项比较的是同一条“intent → 执行 → outcome”时间线的三种恢复情况；工具和崩溃时机不同，不是要把同一个工具的策略中途改掉。

04 / 从实验归纳恢复规则

	
恢复不是猜工具“应该做完了”，而是根据磁盘上最后保存的证据决定下一步。partial 是执行中已观察并保存的部分输出，不是完成证明。

	

		
日志证据恢复动作为什么

		
			
assistant 请求工具，但没有 intent补“未到执行边界”的错误结果检查通过且 intent 保存成功前，不允许执行

			
safe intent，没有 outcome声明匹配且当前仍 safe 才重跑作者允许重跑，但不保证数据不变

			
unsafe／工具缺失／声明变化保留 partial，补明确的 interrupted（中断）错误不能把未知副作用放大成重复执行

			
outcome 已保存，没有结果消息只补 toolResult 消息结果已经存在，不应再执行

			
最终 assistant 已保存，没有 run_end按 stopReason（结束原因）补这一轮的结束记录无需再生成一次模型回复

		
	


	
05 / 为什么日志的最后几行不等于当前对话？

	
想从旧输入之前重新尝试，不必删掉旧回复。每条记录用 parentId 指向它接续的上一条记录，leaf 则是当前对话走到的末端。branch（分支）只是把这个末端移回旧记录。

	
A → B → C    旧分支仍在文件
└→ D → E    当前 leaf = E

物理顺序：A, B, C, D, E
当前路径：A, D, E

	
branch(A) 只移动内存 leaf；下一条 D 的 parentId 指向 A。reopen 默认选择物理最后一条有效 entry，再走 parent 链。全 session 的 requestId 去重读所有 entry，不只读当前路径。

	
若 branch 落在未完成工具的节点，新的 submit 先恢复这个 turn，再写新输入。不同请求或策略变更在持久化等待期间也互斥；不能趁 fsync 未完成偷偷改 live state。


	
requestId 是一次用户请求的唯一标识。同一个标识重复提交时，返回原来的 submission，不追加、不再请求模型。即使原请求中断了，也不会靠同一个 id 自动重试；新的用户操作要用新的 id。

	
如果只在内存记住 requestId，重启就会忘；如果只查当前分支，切走旧分支就会漏。必须查整个 session 文件，才能避免同一个请求再次触发执行。


	
06 / 看懂之后，再对照实现

	

		
SessionJournal：保存记录
首行是 version=1 的 session header。其后每行一个 entry（日志记录），带 id / parentId。先写入，再 fsync，再改变内存；完整旧记录不改、不删。
.mini-agent/sessions/<epochMs>_<uuid>.jsonl

		
AgentSession：包住执行入口
submission 先保存，再请求模型。内部监听器先保存 assistant、工具结果和 run_end，再通知外部订阅者。CLI 默认新建，--continue 恢复当前目录最新文件。

	

	
现在再看完整顺序：prepare 是执行前的参数、权限与中断检查；toolResult 是提供给模型的工具结果；run_end 标记这一轮结束。每个“保存”都要等 fsync 完成。

	
保存 submission → 请求模型 → 保存 assistant → prepare
→ 保存 tool_intent → execute → 保存 tool_outcome
→ 保存 toolResult message → 保存 run_end

	
parallel（并行）多了一道全批屏障：先完成本批所有 prepare 和 intent 保存，再启动任一个 execute。第二条 intent 保存失败时，本批执行次数为 0；第一条已保存的 intent 仍留在日志里，供以后恢复判断。

	

		进阶边界：恢复到哪里，以及日志尾部损坏怎么办
		
级别 2 指修复到完整 turn（这一轮输入及已有响应）的边界。不做任意 step checkpoint、provider 自动生成恢复、task graph、compaction、/fork 或 CLI 树选择器。只有 submission 的崩溃保留 user-only 历史，不自动重发。

		
torn tail（写到一半的末尾残片）：仅容忍末尾无换行且无法解析的一条 fragment。经用户批准，open 校验完整前缀后只截掉这个残片并 fsync；完整 JSON 仅缺最后换行时补换行。否则下一次 append 会拼进残片，导致日志无法再打开。中间坏 JSON、换行结束的坏 JSON、重复 id、缺 parent、未知版本仍必须报错。
