先分清三条时间线

网络：任意 bytes chunks显示：start / delta / block end 历史：完整 done / terminal 诊断 
网络 chunks ── TextDecoder + 行缓冲 ── SSE 帧
SSE 帧     ── JSON + 协议状态机 ────── AssistantMessageEvent
统一事件   ── core 映射 ────────────── AgentEvent → CLI
message_stop ── 参数解析 / stopReason ── done → 完整 assistant 入历史
先记住这句话

网络 chunk 不是事件，block 结束不是回复结束，partial 不是可执行参数。这三个“不是”分别是 SSE 解析器、响应状态机与 core 工具保护存在的理由。

一帧 SSE 的真实长相

后面所有章节都在处理这样的文本。它只是「键: 值」的行，空行才是一帧的边界——这就是“网络 chunk 不是事件”的具体所指：

event: content_block_delta
data: {"type":"content_block_delta","index":0,"delta":{"type":"text_delta","text":"你好，"}}

event: content_block_delta
data: {"type":"content_block_delta","index":0,"delta":{"type":"text_delta","text":"文件已读。"}}

event: message_stop
data: {"type":"message_stop"}

取自 fixtures/text.sse。模型的一句“你好，文件已读。”在 wire 上是三帧：两个文本碎片 + 一个结束信号。

名词表（第一次看到再展开）

SSE（Server-Sent Events）：HTTP 响应体上的一种纯文本流格式，服务器按帧持续推送，本页上图就是它的全部语法。

IR（中间表示）：我们自己定义的消息结构（user / assistant / toolResult），与任何 provider 的协议无关；anthropic-messages.ts 负责 IR ↔ wire 的双向翻译。

partial：还在生长中的半截 assistant 消息，每个 delta 都在原地改它；只供 UI 即时显示，不进历史、不可执行。

done：整次回复被证明完整（收到 message_stop）后才发出的终止事件，携带权威完整消息——只有它能进历史。

terminal：done 或 error 的统称；一次请求必须恰好以一个 terminal 收尾。

stopReason：模型为什么停下——stop（说完）/ toolUse（要调工具）/ length（被 max_tokens 截断）/ error / aborted。

本页交互是离线教学模拟，不发送 API 请求、不读取 key、不执行真实工具。源码已实现，本地 HTTP 验收已覆盖；真实 Kimi 联调已于 2026-10-14 执行：流式文本 → read 工具回喂 → 最终总结完整走通，并确认了网关会主动返回 thinking block（适配器显式跳过）。

网络边界：半个中文字符不是坏 JSON

	
“你”的 UTF-8 是三个字节。网络可以在第一个字节之后截开。若每个 chunk 都单独 decode，半截字符变成 �；若使用 decode(chunk, { stream: true })，decoder 把半截字节留到下次。

	

		
逐 chunk 实验 · 故意切开“你”和“好”的 UTF-8

		

			
本次 bytes（十六进制）

			
错误做法：每块独立 decode

			
正确做法：流式 decode + buffer

			
只有遇到空行才派发

		

		

		
这个实验只演示一帧 LF data。生产 readSse 另外处理 CRLF/CR、多条 data、注释、EOF、fatal 解码与 reader 清理；不要把教学实验当作可复制的完整 parser。

	

	
帧解析器为什么不负责 JSON.parse？

	
// packages/ai/src/sse.ts（节选）
const decoder = new TextDecoder("utf-8", { fatal: true });
buffer += eof ? decoder.decode() : decoder.decode(chunk.value, { stream: true });
// 按行积累 event 与 data；空行才派发：
if (data.length) yield { event, data: data.join("\n") };

	
SSE 帧只知道 event/data。下游才知道 input_json_delta 与 message_delta。分开之后，中文分片 bug 能在 sse.test.ts 中单独定位，不必同时猜模型状态。

	
前端类比
fetch body chunk 像 socket 收到的字节批次；SSE 帧像一个完整消息 envelope。不要把 TCP/HTTP 的“刚好读到多少”当成应用层的“刚好一条”。

6
模型边界：工具结果为什么穿 user 的外衣

	

		
内部 IR
assistant:
  text("先读两个文件。")
  toolCall(c1, slow_read, {path:"a.txt"})
  toolCall(c2, fast_read, {path:"b.txt"})
toolResult(c1, "a.txt")
toolResult(c2, "b.txt")

		
Anthropic wire
assistant:
  text("先读两个文件。")
  tool_use(c1, slow_read, input)
  tool_use(c2, fast_read, input)
user:
  tool_result(tool_use_id:c1)
  tool_result(tool_use_id:c2)

	

	
toolResult 不是用户真的打了一句话。这是 Anthropic 的传输协议；IR 保持自己的语义角色，adapter 在边界转换。相邻同角色 wire 消息合并 blocks，连续结果不排序，源顺序仍为 c1 → c2。

	
工具执行事件： end(c2) → end(c1)          // 给实时 UI
历史消息：     toolResult(c1) → toolResult(c2)
下一次请求：   user[tool_result(c1), tool_result(c2)]

	
转换器创建新的 arrays/blocks，不修改原历史；schema 变成 input_schema，execute、replay、executionMode 都不发送给模型。阶段 8 尚未开始，system 仍取 context.system.content。

	
中断后的配对
如果顺序批次只完成 c1 就被取消，下一次不能只跳过 aborted 诊断：c2 的 tool_use 仍需要配对。转换器仅在 wire 副本中补一个 c2 的 is_error: true 结果，说明前一回合中断、不能假定成功；保留 c1 的真实结果和调用源顺序，不执行 c2，也不修改历史。缺少结果不等于工具没有产生副作用，因此不能自动重试。

两个容易忽略的边界：计量与错误归属

	
7.1 Token 不做逐帧求和

	
input_tokens                = 10  // uncached
cache_read_input_tokens     = 20
cache_creation_input_tokens =  5
Usage.inputTokens           = 35

message_delta.output_tokens: 2 → 7
Usage.outputTokens:          7     // 覆盖累计值，不是 2 + 7
cost:                        未提供 // 不是 0

	
cacheReadTokens/cacheWriteTokens 作为子计数保留；未来计算成本时，必须分别计价。durationMs 由 event stream 的单调时钟结算，done 和 error 都有收尾时刻。

	
7.2 三种错误，三个负责人

	

		
错误谁处理可观察结果

		
缺 key / 非法 URL / maxTokens≤0配置工厂，生命周期前throw；CLI 明确失败，不退回 fake

		
HTTP / SSE / EOF / abortprovider 泵 + 状态机terminal error；正常结束 run

		
listener rejectAgent 交付边界abort run signal 停止后台读取；prompt reject 原错误，不递归合成第二条 error

	

	
状态机的内部 diagnostic formatter 在 error push 之前脱敏；HTTP 错误只显示状态码，拒绝自动 redirect。若成功 terminal 之后 reader cleanup 才失败，结果不能改写，只输出脱敏 cleanup 日志。

	
为什么不立即重试 HTTP 错误？
网络失败不等于服务端没执行；模型请求可能已消耗额度，而此前工具可能已有副作用。自动重试需要单独定义幂等与恢复语义，本阶段不偷跑阶段 9。






	
8
把决策说清楚，而不只是记住 API

	
① 为什么 StreamFn 不返回 Promise<AssistantMessage>？
只有最终 Promise 无法表达增量；而 Promise<Stream> 又不必要地把拿到消费句柄推迟到 HTTP 完成。同步返回 stream，异步泵 push，让显示与生产解耦。

	
② 若 toolcall_end 就开始执行，会怎样？
那时还不知道整次 stopReason。后面的 max_tokens 可能说明另一条参数被截断；提前执行第一个调用就绕过了整批 length 保护，也破坏“done 才可入历史”的边界。

	
③ EOF 为什么不能算正常 stop？
EOF 只证明连接结束，不能证明模型回复结束。只有 message_stop 提供成功证据；没有它的半截回复可能缺 JSON、usage 或后续 content blocks。

	
④ 为什么 core 必须先判断 error，再筛工具？
即使一个坏 provider 在 error 消息里带了 toolCall，也不该执行。失败状态不是工具授权；这道 guard 保护所有 StreamFn 实现，而不只保护 Anthropic。

	
⑤ 谁该处理 listener reject？
这是 UI/持久化交付失败，不是模型网络故障。Agent abort 自己拥有的 run signal，停止无人消费的读取，再保留原异常；provider 不认识 listener，不能把交付失败包装成模型能纠正的错误，也不能向已失败的 listener 补发第二套终止生命周期。

	
⑥ 为什么两个工具完成得乱序，发给模型仍有序？
tool_execution_end 是实时反馈，toolResult 是模型协议历史。Promise.all 的输入 index 保序；转换器忠实使用历史顺序，不再按时间重新排列。
