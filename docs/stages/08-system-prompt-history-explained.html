System prompt
为什么要变成历史？

阶段 7 已经把真实 provider 接通；阶段 8 不增加“更聪明的模型”，而是修正一处更基础的状态建模：prompt 与模型可见工具集不再是一份随时会变的当前值，而是一串可以重放、持久化、裁剪和审计的历史事件。

先看结论 ① 旧模型的问题 ② 新消息形状 ③ 重放模拟器 ④ 重放算法 ⑤ Agent 怎么改 ⑥ 买到什么 ⑦ 实施顺序 ⑧ 回测

先看结论：参数描述现在，历史解释现在

阶段 1–7

“当前值”模式

Agent {
  system: "You are..."
  state.messages: [...]
  state.tools: [read, bash]
}

历史只记录对话；prompt 与工具放在旁边。恢复会话时必须额外记住“当时那份 system/tools 到底是什么”。

阶段 8 之后

“事件历史”模式

messages = [
  SystemMessage(base + read + bash),
  UserMessage(...),
  AssistantMessage(...),
  SystemMessage(extra - bash + edit)
]

当前 prompt 与工具不再单独存。只要按顺序重放 system entries，就能重新得到现在。

这个阶段唯一的新概念

当前状态是历史的函数。阶段 8 不做 JSONL 持久化、不做上下文压缩、不做扩展系统；它只把三者将来依赖的地基先改对。

1

为什么现在必须回头改？

恢复会话

历史缺了一块

如果只持久化 user/assistant/toolResult，恢复时还得从别处找 system 与 tools。两份状态一旦不同步，恢复出来的就不是原会话。

Prompt cache

前缀必须稳定

每轮重建、重排或重复插入 system 都会改变请求前缀。相同配置不新增 entry，provider 才能命中稳定前缀。

上下文压缩

不能把规则一起删掉

阶段 10 会裁剪旧 conversation。若规则属于独立参数，裁剪器必须额外同步；若规则就在 transcript，保留 system entries 后自然仍能重放。

动态工具

“什么时候可用”也是事实

阶段 11 会切换工具。直接覆盖当前数组会抹掉过去；追加 toolsAdded/toolsRemoved 才能解释某个历史时刻为什么模型看见这些工具。

阶段 7 留下的最后一个直接读取点

// 当前 packages/ai/src/anthropic-messages.ts
return {
  system: context.system.content,
  messages,
  tools: context.tools.map(...),
};

这里本身没有错；错的是 context.system 与 context.tools 目前由“旁边的当前字段”提供。阶段 8 会保留 StreamContext 形状，但让这两个字段变成 transcript 的重放快照。

2

新的 SystemMessage 长什么样？

消息 IR

interface SystemSection {
  tag?: string;
  text: string;
}

interface SystemMessage {
  role: "system";
  sections: SystemSection[];
  toolsAdded?: Tool[];
  toolsRemoved?: string[];
}

三个字段各表达一个事实

字段语义
sections从这个时间点起追加的新指令段落
toolsAdded从这个时间点起模型可以看见的完整工具声明
toolsRemoved从这个时间点起停止可用的工具名
System #1
base + read + bash
Conversation
user / assistant / tools
System #2
repo-only - bash + edit
Replay snapshot
base + repo-only / read + edit

tag 只是元数据，本阶段不会自动把它写进 prompt。真正发给模型的是非空 section text 按历史顺序用空行连接。工具变化在同一条消息中先 remove 再 add，因此同名工具升级可以表示为“移除旧声明，再加入新声明”。

4
重放算法其实很朴素

		

			

				
Prompt fold

				
sections = []

for message of transcript:
  if message.role !== "system":
    continue
  sections.push(...message.sections)

prompt = nonEmptyText(sections)
  .join("\n\n")

			

			

				
Tool fold

				
tools = Map<name, declaration>()

for systemMessage of transcript:
  for name of toolsRemoved:
    tools.delete(name)
  for tool of toolsAdded:
    tools.set(tool.name, clone(tool))

currentTools = [...tools.values()]

			

		

		
顺序为什么重要？
同一条 delta 若包含 toolsRemoved:["read"] 与新版 toolsAdded:[readV2]，先删后加才能让新版留下。Map 还会给出稳定、可预测的工具顺序。

		
为什么还要计算 tool state changes？

		
Agent.setTools(next) 不能每次都追加一份全量工具。它先比较当前 replay declarations 与 next declarations：

		
相同声明、不同对象引用   → 不写 system delta
只替换 execute 闭包       → 更新执行注册表，不写 model-visible delta
新增工具                  → toolsAdded
删除工具                  → toolsRemoved
同名 schema/description 变 → toolsRemoved + toolsAdded

CLI
system: string
新会话简写

			
Agent state
prepend initial
SystemMessage once

			
agentLoop
replay transcript
build snapshot

			
Anthropic adapter
render string/tools
skip system entries

		

		

			
组件阶段 8 后的职责不负责什么

			
CLI / AgentOptions给新会话提供初始 system string 与 ToolDef不手写 SystemMessage，不维护 replay

			
AgentState.messages保存完整 transcript，是 system/tool 状态的权威历史不保存单独的 currentSystem 字段

			
AgentState.tools保存带 execute 闭包的运行时注册表不决定模型当前看见哪些工具

			
agentLoop每轮重放 system/tools；只允许 active declaration 对应的 ToolDef 执行不修改旧 system entries

			
provider adapter把 replay snapshot 转成 Anthropic 顶层 system/tools不各写一套历史重放规则

		

		
一个容易漏掉的安全边界
工具已经从 transcript 移除后，即使旧 execute 闭包还留在注册表里，也不能执行。模型可见集合与可执行集合必须同时受 replay state 限制，否则“移除工具”只改了 UI，没有改能力。

O(1) 读取变成 O(n)，具体买到了什么？

		

			

				1 · 持久化免费
				
Resume 不再猜配置

				
阶段 9 只要恢复 transcript，就同时恢复了当时的 prompt 与模型工具状态，不需要另一份 sidecar 配置。

			

			

				2 · Cache 稳定
				
没变化就不写新 entry

				
连续请求重放出相同 system/tool 前缀。相同工具声明只更新运行时闭包，不污染模型输入。

			

			

				3 · 压缩天然正确
				
裁剪 conversation，保留 rules

				
阶段 10 可以删除旧 conversation context，同时保留 system entries；重放结果不变。

			

			

				4 · 变化可审计
				
工具何时出现/消失有证据

				
阶段 11 动态切换工具时，历史能解释某次请求为何允许 edit、为何后来不允许 bash。

			

		

		
代价是每轮请求前扫描 transcript。教学规模下，这段本地纯函数成本远小于网络延迟；更重要的是它用一点 CPU 换掉了多份状态同步的正确性风险。

Task 1
IR + replay helpers
改 SystemMessage，新增 prompt/tools 重放、初始消息、tool declaration diff。

			
Task 2
Provider 消费 snapshot
Anthropic wire 继续用 string/tools，但数据来自 replay；system entries 不进入 wire messages。

Agent / loop 改权威源
Agent 只写一次初始 system；loop 每轮重放；removed tool 不可执行。

appendSystemSections / setTools 只追加 delta，active run 期间禁止切换。

用户体验保持不变；连续请求验证 system/tool 前缀稳定。

回测：如果能答清这些，就真的懂了

		
为什么不直接在 session 文件旁边再存一份 currentSystem？
因为它会成为第二份权威状态。任何一次 append、branch、resume 或 crash 都要保证两份数据原子同步；把变化写进 transcript 后，当前值只是确定性重放结果。

		
为什么 repeated prompt 不能重复追加同一条 SystemMessage？
它既制造无意义历史，也改变 provider 请求前缀，使 prompt cache 看见不同输入。请求本身不是 system 状态变化，不应写 system entry。

		
为什么 AgentState.tools 还要保留？
SystemMessage 只保存可持久化的模型声明，没有 execute 函数。运行时仍要保存 ToolDef 闭包；但某个闭包是否 active，必须由 transcript replay 决定。

		
同名 read 工具 schema 变化时，为什么不是直接覆盖？
重放 Map 内部最终确实会得到新版，但历史 entry 必须明确表达旧声明停止、新声明开始。remove + add 让变化可审计，也避免把“同一个名字”等同于“同一个协议”。

		
裁剪为什么必须保留全部 system entries？
本阶段 sections 是只追加增量；删掉早期 system entry 就会丢失 base prompt 或旧工具变化。阶段 10 若要合并它们，必须生成等价 replay snapshot，而不是静默删除。

		
为什么接受 O(n) replay？
n 是本地 transcript 长度，网络请求才是主要延迟；换来的收益是 resume、cache、compaction、dynamic tools 共用一个确定性状态模型。若未来性能真的成为问题，可以缓存 replay 结果，但缓存仍只是派生值，不是新权威源。
