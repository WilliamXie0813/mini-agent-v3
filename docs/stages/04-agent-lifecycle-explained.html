1

从两个出口，收敛成一条事件流

名词表（先扫一眼，后面随时回来查）

run：一次 agent.prompt() 从开始到真正 idle 的整个过程，中间可能包含好几轮请求模型。

turn：run 内部的一轮——一次模型请求、它可能带的工具调用、工具执行和结果，算一个 turn。一个 run 可能有好几个 turn（比如模型先调工具，再追问一次才给出最终回答）。

listener：订阅 Agent 事件的外部代码，比如 CLI 把文字打到屏幕、未来往磁盘写 session。Agent 必须等它们处理完事件，才能说这一步「真的做完了」。

backpressure：事件产生的速度不能超过 listener 消费的速度——Agent 发完一个事件会等 listener 处理完再继续，不会把事件堆起来不管。

activeRun / isStreaming / turnOpen / messageOpen：Agent 内部的四个开关，分别回答「这次 run 还没结束吗」「assistant 还在吐字吗」「当前 turn 还没关闭吗」「当前这条 message 还没写完吗」。进阶模式里会实时看到它们怎么开关，鼠标悬停在开关上也会提示含义。

message_update 为什么装两份东西

它连接两个层：内层保留 provider 原始增量，外层给 Agent/UI 一个统一的 message 字段。字段名相似，但职责不同。下面仍然是上一节同一个 run——模型吐出最终回答「done」时，第一个字符 "d" 产生的那个事件：

AgentEvent（core 层）

{
  type: "message_update",
  message: { ...partial },
  assistantMessageEvent: {
    type: "text_delta",
    delta: "d",
    ...
  }
}
两个消费者 · 这是本节的答案，默认展开

CLI 看内层 delta，立即写到 stdout；Agent 的 reducer不处理 update，直到 message_end 才把完整消息放进历史。未来 Web UI 可以用顶层 message 更新消息卡片，而不用理解 provider 的全部协议。

四个回测问题

先口头回答，再点开参考答案。答案不要求背代码，重点是说清「如果反过来做，会失去什么」。

1. 为什么 loop 无状态？

让 loop 只处理一次 run 的过程，可以独立测试；真实 state 只有事件 reducer 一条写入路径，因此 UI、持久化与内存不会各自看到不同版本。

2. 为什么 listener 必须 await？

因为 listener 未来会做持久化等正确性工作。若不等待，agent_end 只表示「通知已发出」，不能表示「本轮副作用已完成」。

3. 为什么要三层事件？

provider delta 只能描述 assistant 内容增长；turn 还包括工具，run 还包括多轮请求。三层让 UI 能分别回答「哪条消息」「哪一轮」「整个任务」是否结束。

4. 为什么 agent_end 只带本轮消息？

完整 transcript 已在 agent.state.messages。事件只带增量，订阅者不必每轮重复接收旧历史，也不必再次计算哪些消息是新产生的。
