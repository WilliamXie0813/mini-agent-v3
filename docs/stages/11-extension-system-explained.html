不用改发动机，
也能加规则

你只想给购物车加优惠券折扣，为什么还得修改 agent 的内部循环？

贯穿任务：让编程助手修改 src/cart.ts，再运行团队自己的 lint_cart 检查。团队要求禁止 shell 工具、少发重复读取、保留检查记录，还想在模型调用外面加观测。这些规则属于团队，不应该每次都塞进发动机。

core 就是“问模型、执行工具、继续下一轮”的核心发动机；工具就是助手能调用的具体动作，例如读文件。src/cart.ts 与 lint_cart 是本页虚构练习，不声称本仓库有购物车产品。

实现已落地；本页是离线教学模拟，不是真实执行界面。

2026-10-16 重新核对 stage-11-extensions 分支、提交 ad4cded 的生产代码和测试：内联扩展、六个决策钩子、第二个 StreamFn 包装器与 CLI 接线已实现。旧版“仅设计”的判断已纠正。下方互动不调用模型、不执行工具、不写日志、不安装包；配套测试会另用真实 runner/core 与本页示例核对关键行为。

01 / 最直觉的方案：哪里需要，就往哪里塞

  1. 在核心工具执行器里加 if：遇到 lint_cart 就检查优惠券。
  2. 再塞一段团队规则：遇到 bash 就拒绝。
  3. 到模型请求代码里删重复读取，再加调用计时。

任务能跑了，但项目规则散落在发动机各处。换一个项目要不要再维护一份 core？升级循环时，谁保证这些分支没有被漏掉？更糟的是，事后监听到危险命令才报警，已经来不及阻止它。

要留的是“继续之前允许规则插话的位置”，而不是让扩展任意读写内部状态。hook（钩子）就是这种决策插口；扩展就是通过受控入口登记工具、命令和规则的一段代码。

02 / 先只认三个角色，不急着背完整流程

扩展：说明“我要加什么”

ExtensionFactory 就是一个接收入口对象的函数。拿到的 ExtensionAPI 只有 on、registerTool、registerCommand：分别登记事件规则、工具、命令。不导入 core 的运行时代码；允许导入类型。

组装方：把规则接到发动机

ExtensionRunner 收集登记项。bootstrapExtensions 顺序初始化扩展，返回 hooks、tools(base)、notify 等接线入口。core 照原有协议工作；新增团队规则不用再改 core。

内联不是“从目录自动找到插件”，而是组装代码直接传入 { name, factory }。当前 CLI 在 packages/cli/src/index.ts 装入 createDemoExtension()：真实示例工具是 word_count，真实规则拒绝所有 bash，不是会识别所有危险命令的安全引擎。

观察事件是“看见发生了什么”；决策事件是“返回什么会改变下一步”。当前 on("tool_call", ...) 是决策，on("tool_execution_end", ...) 是观察。它们不能互换。

03 / 同一个任务，八小课逐步拆开

每课三步：先猜 → 点击揭示 → 看本步卡片 → 下一步。未揭示不能前进。回看或切课会重新藏起答案；JSON 只放在折叠区。

  1. 硬改 core 的代价。
  2. 登记 lint_cart，与内置工具共存。
  3. 执行前拒绝，以及多条规则何时停止。
  4. 按真实顺序准备请求、剪枝，保留原始历史。
  5. 检查完成后整理结果，不倒转已经发生的执行。
  6. 继续一轮，把下一轮说明写成真实历史。
  7. 包装模型函数，认识优先级与创建时机。
  8. 规则出错、观察者出错：为什么后果不同。

04 / 再对照真实名字：事件如何接到六个钩子

		
上下文就是这次交给模型的材料；turn就是一轮模型往返与这批工具处理。runner.sessionHooks() 把事件处理器变成下表六个 core 钩子。没有对应处理器，就不生成那个钩子；零处理器返回 {}。

		

			

				当前代码的精确返回值与组合方式，不以总设计替代实现
				
扩展事件 → core 钩子允许做什么多处理器与边界

				
					
tool_call → beforeToolCall返回 { block: true, reason?, terminate? } 拒绝，reason 成为错误结果文本；抛错也不执行工具。按注册顺序，第一个非 undefined 返回值生效并停止后续处理器。{} 与 { block: false } 也会短路，但不拒绝；“不关我事”必须返回 undefined。

					
tool_result → afterToolCall只覆盖 content 与 isError。不能覆盖 details、durationMs、terminate；不能让被拒工具重新执行。全部运行，按字段合并返回值，后者同字段覆盖前者；void 不擦掉已累积字段。每个处理器收到同一份原始 context，不是上个处理器改写后的结果。

					
context → transformContext过滤、重排请求消息；最终数组必须非空，且元素必须是入参里已有的同一对象。克隆、注入新对象会抛 TypeError。依次传递上一次的数组，undefined 保持当前数组。core 最后检查引用；没有深度冻结，规则作者仍不得就地改消息。系统不自动验证剪枝后语义/工具配对是否合理。

					
before_provider_request → prepareRequest返回整个 StreamContext，替换当次请求材料。可以加请求专用资料，不写入历史。依次传递上一个 context；undefined 不变。AgentSession 内部日志投影与阈值压缩先执行，扩展只装饰其后，不能覆盖会话编排。

					
turn_end → finishTurn返回 { action: "end" | "continue" }。没有工具时默认结束；有工具时默认继续。第一个非 undefined 返回值短路。正常轮次先发 core 的 turn_end 事件，再咨询它；error/aborted、工具批次硬停时不咨询。continue 共用 maxTurns，不是无限续轮。

					
next_turn → prepareNextTurnWithContext从第二轮起，可返回 sections、toolsAdded、toolsRemoved。全部运行：前两项按注册序拼接，移除名去重。非空时追加一条真实 SystemMessage；全空/void 是 no-op。工具增删是声明，不凭空创建 execute 函数。

				
			

		

		

			读完实验后，再看一次真实调用顺序
			
turn_start
→ next_turn（仅 turn ≥ 1；非空结果形成 system 历史消息）
→ 从历史重放 system / 工具声明
→ AgentSession 内部 prepareRequest（重投影、必要时压缩）
→ before_provider_request（扩展请求装饰）
→ 按 prepared.tools 筛选可执行工具
→ context（过滤/重排消息，随后校验引用）
→ StreamFn → 完整 assistant 消息
→ 若有工具：查找/校验 → tool_call → 执行前 intent → execute
   → finalize → tool_result → tool_execution_end → toolResult 消息
→ core turn_end 事件
→ 非错误且未硬停时，扩展 turn_end 决策 → 结束或下一轮

			
上面工具线是单个调用的逻辑顺序。并行批次保持既有规则：准备与 intent 提交屏障之后才运行获准工具；工具 end 按完成顺序，结果消息按模型原调用顺序。截断参数路径直接产生错误，跳过 afterToolCall，不能让扩展抹掉截断诊断。

			
“工具硬停”指整个批次聚合出的 terminate：当前实现是这批所有结果都带 terminate: true；不是任意一个工具说停就无条件停全批。

		

	


	

		
05 / 从卡片落到一份真 API 示例

		
这是可在仓库现有依赖环境运行的纯内存示例：工具只返回示范文本，不读写 src/cart.ts，也不真正验证优惠券。模型使用 createFakeStreamFn 预设回复，不联网。下面代码块与仓库里的真实文件逐字节一致（测试会核对这一点），本页不自动执行它。

		

			展开完整示例：registerTool → hooks → 统一工具执行
			
真实文件在 packages/examples/src/stage11-cart.ts（新增的 @mini-agent/examples workspace 包）。先在仓库根目录 pnpm install 链接 workspace，再用 node --experimental-strip-types packages/examples/src/stage11-cart.ts 运行（沿用仓库 Node 22+ 环境，无需额外新增依赖）。示例用 Agent 不写日志；要持久化，换成 AgentSession 并经 hooks: boot.hooks 注入。

			
import { Agent } from "@mini-agent/core";
import { createFakeStreamFn } from "@mini-agent/ai";
import { bootstrapExtensions } from "@mini-agent/extensions";

const boot = await bootstrapExtensions({
	extensions: [{
		name: "cart",
		factory(api) {
			api.registerTool({
				name: "lint_cart",
				description: "Memory-only coupon teaching check",
				parameters: { type: "object", properties: {} },
				replay: "safe",
				execute: async () => ({
					content: [{ type: "text", text: "coupon checked" }],
				}),
			});
			api.on("tool_call", ({ toolCall }) => {
				if (toolCall.name === "bash") {
					return { block: true, reason: "cart: bash disabled" };
				}
				return undefined;
			});
		},
	}],
});
const agent = new Agent({
	system: "You are a coupon teaching agent.",
	tools: boot.tools([]),
	...boot.hooks,
	streamFn: createFakeStreamFn([
		[{ type: "toolCall", id: "check-1", name: "lint_cart", arguments: {} }],
		"优惠券检查示例完成",
	]),
});
agent.subscribe((event) => boot.notify(event));
await agent.prompt("给 src/cart.ts 加优惠券折扣，然后检查");
console.log(agent.state.messages);


			
boot.tools([]) 是无内置工具的最小演示。真实 CLI 使用 boot.tools(createDefaultTools()) 合并内置工具，先内置后扩展；登记重复扩展工具、合并时撞上内置工具、重复命令名都会抛具名错误，不是后者偷偷覆盖前者。

		

		

			模型插口的真实用法：这是包装，不是 ai-sdk / 第二个 HTTP 客户端
			
StreamFn 是把请求材料与中止信号变成统一模型事件流的普通函数。当前第二实现 createSecondStreamFn(inner, { decorate?, onCall? }) 包装已有函数：可装饰请求、转发全部事件、报告调用前材料与耗时。底层仍是原服务接入；CLI 实际调用的 installStreamFn() 未传 decorate/onCall，只安装转发包装。

			
setDefaultStreamFn(base);
const boot = await bootstrapExtensions({ extensions: [...] });
boot.installStreamFn();
// 内部等价：setDefaultStreamFn(createSecondStreamFn(getDefaultStreamFn()))
// 必须先有 base；没有默认实现时，getDefaultStreamFn 会抛错。

// 新建 Agent / AgentSession：
// options.streamFn 非空 → 用显式函数
// 否则 → 读取此刻的默认函数；构造时捕获，之后不会跟着全局槽变化

			
总设计写过 ai-sdk，实施计划和当前代码选择零新增运行时依赖的自写包装器。本页不再把 ai-sdk 当作已安装或即将由此分支自动提供的能力。AgentSession 的任务请求与摘要请求持有同一个已捕获的函数。

			
ExtensionContext 虽有 getStreamFn/setStreamFn 类型，但 factory 没有拿到这个 context；runner 的私有槽也不负责全局安装。当前 CLI 传给斜杠命令的实现是 getter 返回 undefined、setter 空操作，不能靠命令热切换模型。安装默认包装器的入口是组装方的 boot.installStreamFn()。

			
包装器的异步 decorate/转发错误被编码为流上的 error 事件与错误 assistant 消息，不等于扩展决策钩子的原错 reject；正常转发结束时 onCall 的 ok 仅按最终 stopReason 是否为 error 判定，不应解读成业务校验成功。

		

	


	

		
06 / 哪些会留下来，重启后又不会自动发生什么？

		

			

				
请求视图，不进历史

				
before_provider_request 的装饰与 context 的过滤只作用于本次请求。历史不会因此删除。要保留下一轮说明，应通过 next_turn 生成真实 system 消息，而不是把一个临时请求当事实源。

			

			

				
实际结果与系统更新，会进日志

				
AgentSession 先持久化再通知订阅者。afterToolCall 改写后的内容进入工具 end、toolResult 消息与 outcome。next_turn 的非空结果经 message_start/message_end 进入 journal（逐条追加的日志），重开时可重放。

			

		

		
当前会话传了 hooks 对象（即使 {}）时，已知工具被 block、校验失败或中止，也会在结束事件补记 tool_intent 与 tool_outcome，留下“已经了结、未执行”的结果；日志里有 intent 不证明执行过。未知工具找不到定义，无法补该 intent；完全不传 hooks 保持阶段 10 原路径。

		
恢复不会重新跑整条扩展链。AgentSession.open 先按既有 journal 规则恢复工具，再创建 Agent。已有 outcome 可复用；缺结果而允许 safe 重跑时，恢复函数直接运行匹配的工具，不重新咨询扩展 before/after 钩子，也不自动再问模型。扩展函数与规则本身不序列化到日志；重启需由组装方重新登记工具、hooks 与 provider。不能承诺恢复时会重新做最新权限审批。

		
错误也不能统一“吞掉”：tool_call 抛错时工具不执行，错误成为该工具的结果，run 可以继续；观察者抛错只记带扩展名的日志，后续观察者仍运行；tool_result / context / before_provider_request / turn_end / next_turn 抛错会记录后重抛，由 Agent 解包原错误，让 prompt/submit 拒绝。初始化 factory 失败则报含扩展名的初始化错误。

		

			现阶段明确不提供的能力与容易误读的边界
			
    
				
  • 只有内联扩展：没有 jiti 文件动态加载、npm 扩展分发、热重载或插件市场。
    • 
				
  • 不是进程隔离沙箱；不 import core 运行时代码解决耦合，不限制任意扩展访问系统。
    • 
				
  • 真实 demo 的 context 规则过滤首个文本以 [truncated 开头的工具结果，不是自动重复读取去重器；本页的成组去重是另一个教学规则。
    • 
				
  • next_turn 可记录工具声明的增删，但不会登记执行闭包。新声明没有匹配的既有工具定义，仍无法执行。
    • 
				
  • finishTurn 是有限预算里的控制，不是阶段 13 followUp 队列，也不盖过硬停。maxTurns 耗尽，底层 loop 抛错；Agent 将其记录为错误 assistant 消息，而非钩子原错的基础设施 reject。
    • 
				
  • 观察通知实际只分发 message_end 与 tool_execution_start/update/end 等支持的事件，其他 core 事件被忽略；不能通过观察返回值阻止工具。类型声明有 session_start，但当前 CLI/notify 接线没有实际发出它，不能承诺启动会触发该回调。
    • 
				
  • CLI 已支持 /ext 查看登记项，/demo 运行已登记命令；没有通用的模型热切换命令。原始 core turn_end 观察流与扩展同名决策事件不是同一次通知分发。
