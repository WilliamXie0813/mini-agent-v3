EventStream 图解

一个「推模型」的事件流：provider 按自己的节奏把事件推进来，消费者用 for await 慢慢读，两边谁也不等谁。本页对应 packages/ai/src/event-stream.ts，全部 152 行。

1

为什么需要它：两边节奏对不上

一次模型响应是一串事件：start → text_delta × n → done。生产事件的是 provider（阶段 7 是 SSE socket），消费事件的是 UI 循环。麻烦在于——两边都是异步的，且节奏完全独立：

  • 生产快、消费慢：socket 一瞬间涌进 20 个 delta，UI 还在逐字打印第 3 个。多出来的事件必须有地方放，不能丢。
  • 消费快、生产慢：UI 读完已有事件，下一个 delta 还在网络上飞。消费者必须挂起等待，不能死循环空转烧 CPU。

以前的 AsyncGenerator 是「拉」模型：消费者不喊 next()，生产者就停着。SSE 的字节到达根本不归消费者管，所以拉模型接不上——字节没地方放。EventStream 就是中间那个带缓冲的交接点：

图 1 · 推拉适配
生产者只管 push，消费者只管 for await，谁也不需要知道对方的存在。

FifoQueue：两个栈拼出来的队列

数组当队列用，shift() 是 O(n)——每取一个，后面全体往前挪。这个 21 行的小类用两个栈避开它：进栈到 incoming，出栈从 outgoing；outgoing 空了就把 incoming 整体倒过来。倒一次顺序反转一次，进一次出一次反转两次，负负得正，正好 FIFO。

每个元素一生只被 push 两次、pop 两次，摊还 O(1)。点下面的按钮亲手倒一次：

同一个结构在 EventStream 里被用了两次：一次装事件，一次装「等待中的消费者」——这是下一节。

两条队列的分工

export class EventStream<T, R = T> {
	private queue   = new FifoQueue<T>();                               // 装事件
	private waiting = new FifoQueue<(v: IteratorResult<T>) => void>(); // 装等待者
	protected done = false;     // 流关了吗
	private settled = false;    // 契约完成了吗（见到过 done 事件）
	// …result() 的 promise 及其 resolve/reject
	// …isComplete / extractResult 两个回调
}

两个方向的错配，各由一条队列接住：

方向多余的东西放哪
生产快、消费慢多出来的事件queue — 存着，消费者来了慢慢取
消费快、生产慢挂起的消费者（本质是它的 resolve 函数）waiting — 存着，下个 push 来叫醒
关键直觉

push 一个事件时先看 waiting：有人等就直接交付（事件不过夜），没人等才进 queue 存着。两条队列任何时刻最多一条有货——事件要么在等人，要么人在等事件。

done 与 settled 是故意分开的两个标志：done 回答「流关了吗」（关门后 push 丢弃、迭代收尾），settled 回答「契约完成了吗」——只有 isComplete 命中过（见到 done 事件）才算。第 ⑤ 节会看到这两者的差别就是「正常关门」与「违反契约的关门」的差别。

waiter 到底是什么？

一句话：waiter 不是一个「人」，而是一个函数——消费者挂起时寄存到 waiting 队列里的那个 resolve。把迭代器里那行代码拆开看：

const r = await new Promise(resolve => this.waiting.enqueue(resolve));
  • 第 1 步：new Promise(...) 一构造，executor 立即执行，消费者手里短暂握住自己这个 promise 的 resolve 函数。
  • 第 2 步：它不自己留着，而是 waiting.enqueue(resolve)——把「唤醒我的钥匙」寄存到队列里，然后 await 睡过去。
  • 第 3 步：之后某次 push() 执行 const waiter = this.waiting.dequeue()——取出来的就是这个 resolve。变量名叫 waiter，因为「它主人在等」。
  • 第 4 步：waiter({ value: event, done: false })——调用它 ≡ resolve 那个 promise ≡ 消费者醒来，拿到事件。
  • 第 5 步：end() 时同理，只是拧钥匙时递的是 { done: true }（「没有下一个了」）。
图 · 钥匙的寄存与取用
一句话总结

waiting 队列里躺着的从来不是消费者本身，而是一把把「唤醒钥匙」。push 不需要知道消费者是谁、在哪、有几个——取出钥匙拧一下就行。这是最原始的发布/订阅：一次性订阅，交付即焚。

push()：亲手推一遍

push(event: T): void {
	if (this.done) return;                    // 关门后来的一律丢弃
	if (this.isComplete(event)) {           // 是完成事件 → 顺手结 result() 的账
		this.done = true;
		this.settled = true;
		this.resolveFinalResult(this.extractResult(event));
	}
	const waiter = this.waiting.dequeue(); // 有人等吗？
	if (waiter) waiter({ value: event, done: false });  // 有 → 直接交付
	else this.queue.enqueue(event);               // 没 → 存起来
}

下面是一台活的 EventStream（事件用数字表示，绿色 9 是「完成事件」）。试试这几个剧本：

  • 剧本 A（生产快）：不开消费者，连按 3 次「push 普通事件」→ 事件堆在 queue。
  • 剧本 B（消费快）：先「启动 for await」，再 push → 事件不经过 queue，直接出现在右侧。
  • 剧本 C（完成）：「push done 事件」→ 注意 done、settled 两个标志和 result() 的状态同时变化，且 done 事件本身也会被消费到。
  • 剧本 D（关门后）：done 之后再 push 普通事件 → 被丢弃。

end()：两种关门

end(result?: R): void {
	if (!this.settled) // 没见过 done 就关门 = 契约违反
		this.rejectFinalResult(new Error("event stream ended without a completion event"));
	this.done = true;
	if (result !== undefined) this.resolveFinalResult(result);
	while (this.waiting.length > 0) {       // 叫醒所有挂着的消费者
		const waiter = this.waiting.dequeue()!;
		waiter({ value: undefined, done: true });  // 「没有下一个了」
	}
}

end() 回答的问题：「不再有任何事件了」这件事，要通知谁？——两拨人：await result() 的（由 rejectFinalResult / resolveFinalResult 两行负责），for await 挂着的（由末尾的 while 循环负责）。

路径触发方式result()for await
正常关门 先 push(done)（settled 已 true）再 end(msg) 早已 resolve，end 里的重复 resolve 被忽略（Promise 只 settle 一次） 读完残余事件后自然结束
契约违反 没发 done 就 end()（settled 是 false） reject——绝不让人永远等下去 被 { done: true } 叫醒，正常收尾，然后由上层抛具名错误
回到模拟器

在上面模拟器里试试：直接按「end()」（不先 push done）——看 result() 一栏变红（rejected），这就是「没有栈、没有错误的死锁」被兜底成明确错误的那一行。先 push done 再 end，则是绿的（resolved）。

6

result()：与迭代并行的第二出口

for await 给你的是过程中的每个事件；result() 给你的是终局——那个完成事件里抠出来的权威结果（对 assistant 响应来说，就是 done 携带的完整消息）。同一个流，两个出口，互不干扰：

const stream = createAssistantMessageEventStream();
const finalMessage = stream.result();  // 先拿句柄，不用等
for await (const event of stream) { /* 渲染 delta… */ }
const msg = await finalMessage;        // 迭代结束后，结果早 resolve 了

构造函数里那行看起来很怪的 this.finalResultPromise.catch(() => {}) 是干什么的？

为什么预挂一个空 catch

契约违反时 end() 会 reject 这个 promise。但调用方未必 await result()（循环只用 done 事件）——没人接的 rejection 会变成 unhandled rejection 噪音。预挂一个 noop catch 把 promise 标记为「已处理」；注意这只是个标记，await result() 的人照样拿到 rejection，错误没有被吞掉。

Symbol.asyncIterator：for await 的翻译层

async *[Symbol.asyncIterator]() {
	while (true) {
		if (this.queue.length > 0) {
			yield this.queue.dequeue()!;          // ① 有存货 → 直接给
		} else if (this.done) {
			return;                              // ② 没存货且关门 → 迭代结束
		} else {
			const r = await new Promise(res => this.waiting.enqueue(res)); // ③ 挂起
			if (r.done) return;                   //   被 end() 叫醒
			yield r.value;                        //   被 push() 叫醒
		}
	}
}

三个分支对应三种现场，其实就是第 ③ 节的两个方向再加一个收尾：

  • ① 队列有货：生产快的时候攒下的，逐个 yield 出去。
  • ② 队列空了、流也关了：return，for await 的循环体停止执行。
  • ③ 队列空了、流还开着：这是整个文件最精妙的一行——new Promise(res => this.waiting.enqueue(res))：造一个 Promise，把它的 resolve 函数存进 waiting 队列，然后 await 它。此后消费者就睡在这里，直到某个 push()（交付事件）或 end()（发 {done:true}）来调用这个 resolve 把它叫醒。

「挂起」在 JS 里没有任何特殊语法——就是 await 一个 resolve 权被交出去的 Promise。waiting 队列里躺着的，正是一个个这样的 resolve。
