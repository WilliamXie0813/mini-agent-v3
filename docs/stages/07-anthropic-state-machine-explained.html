第一遍：正常工具调用
默认场景中停在第一条参数 delta。比较 blocks[0].json 与 partial.content[0].arguments。再走到 block_stop：open 变 false，但 arguments 仍是 {}。

		
第二遍：两个 stopReason
停在 message_delta：局部 stopReason 变 toolUse，但 partial.stopReason 仍 pending。最后一步的 done.message 用完整结果里的 stopReason 覆盖 pending。

		
第三遍：比较失败
先选 length，再选没有 message_stop 的 EOF。前者有成功终止证据，但输出被截断；后者连响应完成都无法确认。两者都不能执行半截工具，却不该混为同一种结果。

blocks[index]这个块还开着吗？它自己的参数字符串拼到哪里了？所有工具共用的一个 JSON 字符串

把几个容易混淆的边界说清楚

	
工具 JSON 已完整，为什么 block_stop 时仍不能执行？
还不知道整次 stopReason。后面可能出现 max_tokens；本阶段 core 的规则是 length 整批不执行，即使某一个工具参数完整。参数在 message_stop 才解析，工具执行更在状态机之后。

	
state.completed 和 stream.end() 是一件事吗？
不是。completed 是状态机防止重复终止、继续解析的控制状态；HTTP 泵看到它会停止读帧。stream.end() 是事件流的资源/迭代收尾。本页只模拟前者，没有网络连接或 EventStream 的时钟结算。

	
thinking 为什么显式跳过，而不是报错？
2026-10-14 真实联调发现：Kimi 在未请求 thinking 时仍主动返回 thinking 语义块，报错会让正常响应全部失败。当前 IR 没有 thinking 块类型，所以状态机显式跳过：校验它的开闭与 delta 类型（thinking 块里出现 text_delta 仍抛协议错误），但它不进 partial.content、不发事件、对 UI 不可见。这不是静默丢弃——选 thinking 场景可以逐帧看到这个块的生命周期。正式支持留待后续阶段。

	
两个工具会不会把参数拼到一起？
选“文本 + 两个工具”场景，看 index 1、2 各自的 json。blocks 与 provider 的块序号对齐，每个 input_json_delta 只追加到对应 index。注意 contentIndex 是 wire 上的块序号：有 thinking 被跳过时，partial.content 只收 text / toolCall，两者的下标不再一致——选 thinking 场景看 index 1 的 text 块。

	
message_delta 的 usage 为什么不是逐帧累加？
输入总量是 uncached + cache read + cache creation。样本中是 10 + 20 + 5 = 35。output_tokens 是累计值，后续帧覆盖，不把旧累计值再相加。本页不计算成本。

	
正常完成遇到坏工具 JSON，能不能用 {} 修补？
不能。只有 length 场景允许用 {} 保留调用身份，同时记录截断诊断，随后 core 整批判失败。正常 toolUse 下的坏 JSON 必须 error；偷偷用 {} 会把协议失败伪装成可执行调用。
