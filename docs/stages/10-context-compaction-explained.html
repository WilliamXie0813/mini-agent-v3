MINI-AGENT / STAGE 10 / 从零理解上下文压缩

对话太长了，怎么办？

你和 Agent 已经改了半天代码。再贴一份日志，模型突然说：“装不下了。”

删掉前面的对话，就可能忘掉“不要改接口”这样的约束；全部带上，又超过模型能接收的容量。阶段 10 做的不是让模型无限记忆，而是：原始记录一条不删，下一次请求只带摘要和最近一段原文。

不需要先读源码。先弄懂“模型这次看到了什么”，再亲手走一遍压缩；函数名和日志字段放到最后。

01 / 先别谈压缩：模型每次到底看什么？

在这个 Agent 的模型请求里，模型能依据的是本次发送的规则、对话和工具声明，不是你电脑上的整份会话文件。你上次说过的话，要被程序再次带入这次请求，模型才能继续据此回答。保存到磁盘和发送给模型，是两回事。

一次请求，像摊在桌上的材料

system：规则，例如“改代码前先读文件”。

user：你的需求，例如“修复负数总价，接口不要变”。

assistant：模型的回复，也可能是在请求调用工具。

toolResult：工具返回的内容，例如读出的源文件。工具声明则告诉模型有哪些工具可以用。

桌子不是无限大的

token 是模型计量文本的单位，不等于字数，也不是“一条消息”。一大段文件内容可能占很多 token。

上下文就是本次请求提供给模型的材料；上下文窗口就是它的容量限制。

材料越积越多，就要提前腾出余量。代码用 token 估算和已知用量判断，估算不等于精确分词，因此也要准备“真的装不下”时的恢复路径。

阶段 9 回答“退出后，对话还在吗？”；阶段 10 回答“对话都在，但这次不能全给模型看，怎么办？”

02 / 不是删笔记，而是准备一份短版材料

下面始终用同一件事举例：修复 src/total.ts，让折扣后的总价不小于 0，同时保留现有导出接口。先看几个直觉方案的后果。

如果这样做会失去什么阶段 10 怎么做
真把旧消息删掉原始要求没了，回头查证或从旧位置重新尝试也做不到。磁盘历史只追加；旧内容仍然在。
只给模型最后几条可能丢掉“接口不能变”的约束，也可能只留下工具结果、丢了对应调用。旧内容整理成摘要，最近的调用与结果完整保留。
把摘要只放在内存进程一退出，下次就不知道该用哪份摘要。把摘要和保留边界作为一条新记录写入历史。

磁盘上的完整笔记

规则 → 原始需求 → 讨论 → 读文件的调用与结果 → 回复 → 新增一张摘要便签

压缩之后，这本笔记甚至多了一条记录。磁盘文件不会因此变小。

为下一次请求准备的短版

完整规则与工具声明 → 摘要 → 最近保留的原文

没有发送的旧原文仍在笔记里，但模型这次不能直接看到。这个“从完整笔记组装请求”的过程，代码叫 projection（投影）。

所以，“压缩上下文”不是压缩文件，也不是无损打包；它是用有损的文字摘要，替代这次请求中的一部分原文。

03 / 先手动走一遍，暂时不管自动触发

第一个实验只回答四件事：哪些原文进摘要？摘要怎么生成？保存在哪里？模型随后看到了什么？看完再继续工具边界、阈值与超窗，不必一次记住所有场景。

04 / 现在才问：什么时候自动压缩？

		
手动压缩是你输入 /compact。自动压缩则在每次任务模型请求前检查，包括工具结果返回后的下一次请求。代码里的 threshold 就是“请求前阈值”，overflow 就是“提供模型服务的一方真的报了超窗”。

		

			
拖一拖：刚好 80，和超过 80 一样吗？

			
把窗口缩小成 100 格、预留量设为 20 格：检查线 = 100 − 20 = 80。这里仅演示比较规则，不是真的发送请求，也不计算摘要会占多少格。

			
			
			
			

			
代码是 tokens > window − reserve，不是 >=。越过检查线不代表已经超出窗口：它是在真正装不下之前尝试腾空间，而不是容量保证。

		

		

			

				
入口何时发生关闭自动阈值后

				
					
手动 manual会话空闲时输入 /compact，不把这条命令存成用户请求。仍可用。

					
请求前 threshold估算用量严格超过检查线，尝试压缩，再组装请求。enabled: false 关闭的只有这一项。

					
超窗后 overflow识别结构化超窗错误，成功压缩后最多给一次恢复重试。仍可用；不是无限救火。

				
			

		

		

			用量怎么估？为什么不能一直用上次的数字？
			
usage 是模型服务返回的用量。这里优先用压缩之后最近一条有效 assistant 的 inputTokens + outputTokens 校准，再加后续消息的粗估用量。缓存读写已经包含在 inputTokens 中，不能重复加。

			
压缩前的 usage 量的是旧的大上下文，即使那条回复仍在保留区，其用量也不能套到新请求上。没有新的有效 usage 时，对整个投影逐条用 ceil(字符数 / 4) 粗估。系统规则和工具声明也占空间；错误、中断和全零用量不能做校准点。

			
实际默认：contextWindow = 128000、reserveTokens = 16384，检查线为 111616。CLI 可用 ANTHROPIC_CONTEXT_WINDOW 配置窗口；reserve 必须小于 window，不是任意正整数都能与默认预留量搭配。

		

	


	

		
05 / 看懂压缩，也要知道它救不了什么

		

			
摘要有损，不保证“一定记住”
摘要要求保留目标、约束、文件路径、错误和未完成工作，但仍可能遗漏细节。旧原文在磁盘，不代表本次模型能直接看到它；保留原文是为了追查与回退，不是让摘要变成无损存储。

			
没材料可摘要，就不强压
有效 assistant 数量不足，或保留边界前根本没有可摘要对话，手动压缩就返回“nothing to compact”：没有摘要请求、没有压缩事件、没有新记录。超窗恢复也可能因为没有候选前缀而无法重试。

			
压完，也不保证一定装得下
最近保留的内容、系统规则或工具声明本身仍可能很大；摘要也可能不够短。请求前阈值路径不会在原地一直压到变小；超窗恢复只有一次机会，仍失败就明确报错。

			
输出被截断，不是输入超窗
stopReason: "length" 是模型输出达到上限，不是 errorKind: "context_overflow"。不能看到“长度”就触发压缩。摘要本身被截断也算摘要失败，不保存半份摘要。

		

		
再输入一次 /compact 不一定无事可做：当前实现可能把上一份摘要本身再次作为候选前缀。是否有候选要看当前投影，不能用“刚压过”代替判断，也不能承诺每次都更短。

		

			一分钟自测：先自己回答，再展开
			
压缩后磁盘文件变小了吗？没有，新增压缩记录，完整旧字节不动。

			
只保留工具结果，能靠摘要代替调用吗？不能。调用和结果必须配套；算法从最近的有效 assistant 选边界，它后面的结果一起留下。

			
旧摘要和新摘要要并排给模型吗？不用。旧摘要进入下一次摘要请求；当前路径上最新的压缩记录决定这一份上下文。

			
切回压缩前的位置呢？那条路径没有后来的压缩记录，组装请求时恢复该位置之前的原文。原文能回来，正因为从未删除。

			进阶：运行中的 Agent 为什么不能立刻换掉？
			
Agent 是负责本轮模型与工具执行的运行对象。手动压缩发生在空闲时，保存后可以立刻按新投影重建它。请求前或超窗恢复发生在本轮执行中，只追加压缩记录、更新本次请求材料；等旧 Agent 完全结束，再重建供下一次使用的对象，避免丢掉事件与中断信号的归属。

			
自动选点与日志校验不是同一件事：findCutPoint 只选有效 assistant；日志校验允许当前祖先路径上的 submission 或非 toolResult 的 message。不要把“允许保存的边界”误读成“自动算法会选的边界”。

			
手动摘要失败时，CLI 打印诊断并回到提示符，不输出摘要正文。摘要不是继续执行任务，也不会因为读到旧工具调用就重新运行工具。本阶段没有新增可交互分支选择器、通用扩展系统、第二 provider 或 /fork 命令。
