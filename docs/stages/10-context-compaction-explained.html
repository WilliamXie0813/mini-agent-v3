MINI-AGENT / STAGE 10 / CONTEXT COMPACTION

装不下，也不删

对话长到模型装不下，删掉最早的消息是最简单的办法——为什么这个工具偏偏一条都不删？

删了，branch 就再也回不到原文；不删，下一次请求又超窗。这页先让你遇到这个两难，再一步步看「摘要 + 保留尾巴」的投影如何两全。

01 / 先试几个直觉方案：哪里会出事？

直觉方案会出什么事因此需要什么
直接删掉最早的对话日志被改写，branch 回不到原文，审计也断了。历史 append-only，只追加一条 compaction 记录。
只在内存里换成摘要重启后摘要丢失，下一次请求又超窗。摘要本身也写进日志，重启后能重新投影。
按条数砍掉前 N 条可能把 toolCall 和它的 toolResult 切成两截。切点只落在 user / assistant 边界。
超窗报错就交给用户重来任务上下文全断，之前的工具成果白做。识别超窗错误，自动压缩后重试一次。
永远逐条数字符估算和真实计费偏差越滚越大，要么误触发要么漏触发。用最近一次 usage 校准，之后的增量再粗估。

关键不是“把旧的藏起来就好了”，而是：journal 永远是完整事实；发给模型的只是当前路径投出的一面——最新摘要 + 保留的原文尾巴。

02 / 两个新概念：压缩记录与投影

compaction entry：摘要的收据

大白话：“从这里往前，模型看这份摘要就够了。”它带 reason（manual / threshold / overflow）、summary、firstKeptEntryId 和 tokensBefore，像普通记录一样 append 进日志、等 fsync。它不改 parent 树，不删、不改任何旧行。

projection：给模型看的那一面

大白话：“同一份日志，模型看到的取决于你站在哪个 leaf。”取当前路径上最新的一条 compaction，在 firstKeptEntryId 前插入摘要，其后保留原文。branch 到压缩之前，投影就恢复原文。

完整 journal（事实）→ 沿 parent 链取当前路径 → 找路径上最新的 compaction
→ firstKept 前插入摘要 → 摘要 + 保留尾巴 = 模型上下文

三条触发路径，共用同一个压缩编排。区别只在什么时候动手、动手后谁重建上下文：

manual：用户输入 /compact

session 空闲时执行。压缩落盘后立刻重建 idle Agent。没有可摘要的前缀时返回 undefined——零事件、零请求、零写入。

threshold：请求前的最后一道检查

每次调用模型前估算上下文，严格大于 contextWindow − reserveTokens 才压缩。刚好等于不压缩，避免边界抖动。

overflow：provider 说装不下了

provider 用结构化 errorKind: "context_overflow" 报告。压缩后重试一次；再超窗就正常报错，绝不循环。

enabled: false 只关 threshold 这条自动路径。手动 /compact 和 overflow 恢复仍然可用——一个是用户明说要的，一个是救火，都不该被“自动压缩开关”误伤。

04 / 从实验归纳压缩规则

	
压缩不是“差不多满了就砍一点”，而是每一步都有明确的触发条件和失败形状。

	

		
情况行为为什么

		
			
估算 ≤ window − reserve不压缩，直接发送严格大于才触发；刚好相等不压，避免边界来回抖动

			
切点候选落在 toolResult 上拒绝，继续往前找 assistant / submissiontoolCall 与它的结果必须成对出现，切开就是坏上下文

			
摘要响应 error / aborted / length / 含 toolCall / 空白压缩失败，不写 compaction，原错误重抛不能留下 success 形状的坏摘要污染回放

			
一次 submit 内第二次 overflow不再压缩、不再重试，run 以 error 结束防止“压缩—重试—再超窗”无限循环

			
第二次压缩只有最新摘要生效；旧摘要作为输入被卷进新摘要摘要并列只会越叠越长，违背压缩的目的

			
compaction 之前记录的 usage失效，回退逐条 ceil(chars / 4) 粗估旧 usage 描述的是已被摘要替代的历史，不能再用

			
stopReason: "length"按输出截断处理，不触发压缩恢复那是输出 token 上限，不是上下文装不下

		
	


	
05 / 为什么 branch 到压缩前后，模型看到的不一样？

	
compaction 记录也挂在 parent 链上。投影只认当前路径上的压缩记录——移走 leaf，生效的摘要就跟着变。

	
A → u1 → a1 → u2 → a2 → C1(compaction, firstKept=a2) → u3 → a3   leaf = a3

leaf = a3 的投影：system + 摘要 + a2, u3, a3
branch(u1) 的投影：system + u1              ← C1 不在路径上，原文回来了
branch(C1) 的投影：system + 摘要 + a2

	
firstKeptEntryId 必须是 compaction parent 的既有祖先，且是模型可见的对话边界。缺失、不在祖先链上、或指向 toolResult，append 与 open 都拒绝——宁可打不开，也不让坏边界悄悄投出半截上下文。

	
token 估算也遵守同一条规矩：Usage.inputTokens 已经包含 cache 读写，校准时只用 inputTokens + outputTokens，不能再加一遍。摘要请求自己的 usage 不算会话 usage，否则下一次估算会被一次“不是对话的请求”带偏。


	
06 / 看懂之后，再对照实现

	

		
compaction.ts：阈值、切点、摘要
shouldCompact() 严格大于；findCutPoint() 从尾部反向数 assistant turn，error / aborted 不计入；generateCompactionSummary() 用同一份 streamFn 发独立请求，失败形状明确。

		
session-context.ts：投影
找当前路径最新 compaction，在 firstKept 前插入固定 wrapper 包裹的摘要。streamContextFromSessionPath() 额外排除 overflow 诊断，并从完整历史重算 system 与 tools。

		
agent-session.ts：三条路径编排
manual 落盘后立刻重建 idle Agent；threshold 挂在 prepareRequest 上，每次请求前检查；overflow 挂在 recoverContextOverflow 上，一次 submit 只恢复一次。内部压缩只 append entry，不当场替换正在运行的 Agent。

		
anthropic-error.ts：结构化错误分类
provider 层把 Anthropic / Kimi 的超窗响应分类成 errorKind: "context_overflow"，其余是 "provider"。core 只认这个字段，从不匹配错误字符串。

	

	
现在再看完整顺序：threshold 发生在发送之前，overflow 发生在收到错误之后，两者都汇入同一个内部压缩编排。

	
submit → prepareRequest 估算 → 超阈值？ → compact(threshold) → 重新投影 → streamFn
→ 收到 context_overflow？ → compact(overflow) 一次 → 重试 → 仍 overflow → error 结束

	
事件顺序同样固定：compaction_start 在摘要请求之前发出；compaction entry 写入并 fsync 之后才发 compaction_end(status: "completed")。失败时发成对的 compaction_end(status: "error")，再重抛原错误。

	

		进阶边界：阈值估算、CLI 入口与不做什么
		
估算优先用 compaction 之后最后一条有效 assistant usage 校准（inputTokens + outputTokens，不含 cache 字段），其后的增量消息逐条 ceil(chars / 4)；找不到有效 usage 就全量粗估。error / aborted / 全零 usage 不做校准点。

		
CLI 用 ANTHROPIC_CONTEXT_WINDOW 覆盖默认 128000 窗口；非法值（0、负数、小数、非数字）启动即失败并报出变量名。/compact 在输入循环里早于普通 submit 分支识别，不生成 requestId，也不会把摘要正文打印到终端。本阶段不做通用 hook 注册表、第二 provider、/fork 或自动定时压缩。

	

	
源码入口：compaction.ts / session-context.ts / agent-session.ts / anthropic-error.ts。阶段 10 源码净增量预算约 380 行；三条路径共用一份压缩编排，是控制预算的关键。
