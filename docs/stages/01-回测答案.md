## 问题 1：为什么 `StreamFn` 是函数类型 + 插槽，而不是 `interface Provider` 及其实现类？

**一句话**：因为调用方只需要"一个能产生事件流的东西"，而接口在只有一个方法时会额外要求一个**承载它的对象**——那个对象没有任何信息，只是语法上的必需。

拆开看三处差别：

### (a) 调用方：`.stream(ctx)` 里的 `.` 是什么？

接口形态下调用点是 `provider.stream(context, signal)`。`provider` 这个接收者是谁？循环对它没有任何其他需求——不查它的名字、不问它的模型、不读它的配置。它唯一的作用是**被点一下**。函数形态下调用点是 `streamFn(context, signal)`，接收者不存在，因为它不携带信息。

这不是美学问题。接收者的存在会传染：只要循环持有 `provider` 对象，`AgentLoopOptions` 就要加一个 `provider: Provider` 字段，测试就要构造一个实现类（哪怕只写一个空对象），而"换 provider"就从**换一个值**变成**换一个实例**。第 7 阶段接真实 Anthropic 时，差值就是 `setDefaultStreamFn(createAnthropicStreamFn({...}))` 一行，对比之下接口形态要新建类、导出类、在 cli 里 import 类。

### (b) 内联灵活性：接口不能内联，函数可以

这是 Pi 真正用到的能力。`packages/coding-agent/src/core/sdk.ts:420` 的 `streamFn` 就是一个**内联的 async 函数**：

```ts
streamFn: async (model, context, options) => {
	const requestOptions = buildRequestOptions(model, options);
	if (options?.sessionId === sessionManager.getSessionId()) {
		cacheWarmer.start(...);
	}
	return modelRuntime.streamSimple(model, context, requestOptions);
},
```

它在调用真实模型之前做了一件**组装期才知道的事**——启动 prompt cache warmer（一个和"我这次请求会长什么样"强相关的动作）。如果 `StreamFn` 是接口，这个逻辑只能落成 `class CacheWarmingProvider implements Provider`，塞进 `provider.ts`，然后才有名字可引用。而它一生只被这一个组装点用一次：**类给它的是名字和文件位置，代价是它从"那里的三行"变成"别处的二十行"**。

函数类型让"组装 = 写一段代码"成立，接口类型强制"组装 = 挑一个类"。前者可以在组装点做组装期该做的事。

### (c) 复杂度：接口会拖出注册表

只有一个方法的接口，落地的必然形态是这样一串：

```
interface Provider
  → class FakeProvider implements Provider   （唯一方法 stream）
  → class AnthropicProvider implements Provider
  → providers 注册表 / 工厂函数 createProvider(name)
  → AgentLoopOptions.provider: Provider
```

而函数形态的全部机制就是 `packages/ai/src/stream-fn.ts` 那 20 行的两个函数体——一个模块级 `let`，一个 setter，一个 getter：

```ts
let defaultStreamFn: StreamFn | undefined;
export function setDefaultStreamFn(streamFn: StreamFn | undefined): void { defaultStreamFn = streamFn; }
export function getDefaultStreamFn(): StreamFn { if (!defaultStreamFn) throw new Error(...); return defaultStreamFn; }
```

Pi 的原话在 `stream-fn.ts:8-9` 的注释里：*"Hosts that provide a default model runtime can install its stream function here **without making pi-agent-core depend on a provider catalog or compatibility layer**."* 那句 "provider catalog" 就是上面的注册表。**接口天然吸引注册表**——有了 `Provider` 这个类型，下一步就是"按名字拿 provider"；有了按名字拿，就有了一张表；有了表，`core` 就认识 provider 世界了。函数类型在结构上不容纳这张表：一个函数值没法被"按名字查"。

### 反面：什么情况下接口才是对的

接口不是坏东西，它的问题是**在这个位置**。判断标准是方法的数量和接收者的信息量：

- **多方法 + 接收者有状态**（`Tool` 有 `name` / `description` / `parameters` / `execute`，还要被注册、被查找、被 CLI 列出）→ 接口/对象是对的。阶段 2 的 `ToolDef` 就是接口形态，因为它真的有四个成员，而且**必须能被按名字查**——这正是 `Provider` 不需要的能力。
- **单方法 + 接收者无状态** → 函数是对的。

同一个项目里两种形态并存不矛盾，判据是同一条：**这个抽象需要被查表吗？需要携带身份吗？**`StreamFn` 两样都不需要，所以它是函数。

## 问题 2：为什么 `packages/core/src/` 里严禁 `import` 任何具体 provider？架构上保证了什么？

**先说怎么证明，再说保证什么。** 因为这条约束的价值全部在于它**可被机器验证**，不能只靠自觉。

### 证明方式：两条 grep

```
$ grep -rn "fake\|anthropic\|setDefaultStreamFn\|createFakeStreamFn" packages/core/src/
(无匹配)

$ grep -rn "while" packages/core/src/
packages/core/src/agent-loop.ts:12:// 阶段 1：只处理无工具的单轮。不写 while 循环…
```

第二条的语境是：阶段 1 的循环里**一个 `while` 都没有**（单轮，不循环）。第二条证明"循环还没长出来"，第一条证明"core 不认识任何 provider 实现"。

`core/package.json` 里确实有 `"@mini-agent/ai": "workspace:*"`，所以**包级别**core 依赖 ai。这正是要点：**依赖的是类型，不是实现**。`core/src/agent-loop.ts` 的两条 import 是：

```ts
import { getDefaultStreamFn } from "@mini-agent/ai";
import type { AssistantMessage, Message, StreamFn } from "@mini-agent/ai";
```

它在 import 什么？`StreamFn` 是 `import type`（编译后消失，`.d.ts` 里连这一行都不会留），`getDefaultStreamFn` 是**读插槽的 getter**——它返回一个函数值，返回什么由组装根决定，core 无从知晓也无从挑选。

### 保证什么

**(1) 换 provider 不动 core，这个承诺是可证伪的。**"换 provider 不改核心代码"是可以空口说的；有了这条 grep 约束，它变成了机器检查项。阶段 7 接 Anthropic 时，如果 diff 里出现了 `packages/core/` 的改动，说明缝没起住——不用辩论，看 diff 就知道。这和"所有 `src` 文件 < 200 行"是同一类东西：把一句设计主张翻译成一条可执行的检查。

**(2) core 可以脱离网络测试，而且永远是。** 阶段 1-6 的默认 provider 是假模型；但即使阶段 7 之后默认值变成真的 Anthropic，`core/test/` 仍然能全绿——因为 core **在结构上不可能**知道默认值是真还是假。`streamFn: createFakeStreamFn([...])` 作为显式参数传进去，和传一个真 provider，对 core 是完全同构的两件事。这一点很实在：一旦允许 `core` import 假模型，反向就成立了——某次图省事在 core 里 `import { anthropic }`，测试就会悄悄开始联网，而 CI 在离线环境里才炸。

**(3) `ai` 的插槽是真的依赖反转，不是"同包内的一个模块"。** 这条是 spec §7.1 里解释为什么阶段 1 就拆包的核心理由，值得原样抄下来理解：

> `stream-fn.ts` 那 20 行插槽要 `import type { AssistantMessageEvent }`。如果类型和插槽在同一个包，插槽只是同包内的一个模块——**依赖反转就没有被证明**。拆开之后，"core 依赖 ai 的类型、不依赖 ai 的实现"这件事是**结构性可见**的。

反过来说：如果 `types.ts` 和 `stream-fn.ts` 和 `fake.ts` 都在 `core` 里，那么"core 不认识 provider"这句话就是**同义反复**——`fake.ts` 在 core 里面，core 当然认识它。拆包把一句话变成了一个可观察的边界。

**(4) 它让"忘记组装"变成具名错误，而不是静默降级。** `getDefaultStreamFn` 在未安装时抛 `"no default stream fn installed; call setDefaultStreamFn() at composition root"`。这个错误之所以可能，正是因为 core **不知道**默认实现是什么——如果它知道，它就会"贴心地"用它，而用户永远不知道自己的组装被绕过。

一句话总结保证：**"core 只认识一个函数签名，不认识任何 provider"——这句话不是注释，是一条 grep 能验的边界；它的收益是换 provider 不动 core，以及 core 永远可离线测试。**

## 问题 3：为什么假模型在 `packages/ai/src/fake.ts`，而不是 `packages/core/test/`？

**一句话**：它是 `StreamFn` 的一个**合法实现**，属于 provider 层；把它放进 `core/test/` 是把它从"实现"降级成"替身"，而降级会同时破坏两件事。

### 判据：它在被谁用？

`fake.ts` 的使用者不是测试，是**生产入口**：

```ts
// packages/cli/src/index.ts:9 —— 生产代码，不是测试
setDefaultStreamFn(createFakeStreamFn(["Hello from the deterministic fake model."]));
```

`pnpm dev`（spec §5 阶段 1 验收第 1 条）走的就是这条路径。这是一个决定性事实：**`core/test/` 是测试目录，按定义不该被生产入口 import**。如果假模型住在那儿，`cli/src/index.ts` 就必须 `import ... from "@mini-agent/core/test/fake-model.ts"`——生产代码 import 另一个包的测试目录，这是结构上的错误，不是风格问题。即便 `exports` 恰好允许（大概率不允许），读代码的人也会立刻怀疑自己看错了。

### 它的身份：同一个契约下的另一个实现

阶段 7 会在**同一个目录**落下 `anthropic.ts`：

```
packages/ai/src/
  types.ts       消息 IR + AssistantMessageEvent
  stream-fn.ts   注入插槽
  fake.ts        确定性实现 ← 住这里
  anthropic.ts   真实实现   ← 阶段 7 住这里
```

`fake.ts` 和 `anthropic.ts` 是同层同契约的两个文件，差别只有一个：一个确定性、一个联网。这不是"测试代码和生产代码放一起了"，而是"provider 层有两个实现，其中一个恰好确定性"。阶段 7 的 diff 因此是最干净的形态——**新增一个文件，改 cli 里的一行**。

### 放进 `core/test/` 会掩盖什么

它会掩盖本阶段最关键的那个事实：**cli 与 core 都不认识任何 provider 实现，只通过插槽安装**。

`core/test/fake-model.ts` 这个路径本身就在暗示"core 拥有一个模型实现"。而这条暗示会让问题 2 的 grep 失效——`grep -rn "fake" packages/core/src/` 仍然空着（目录是 `test/` 不是 `src/`），但读者心里的模型已经错了：他会以为"core 有个假模型，生产时换成真的"，而真相是"core 什么都没有，组装根决定一切"。**约束被满足，理解被破坏**——这比违反约束更糟。

### 一个类比

把假模型放 `core/test/` 像是把 `Map` 的测试替身塞进标准库。假模型不是替身（test double），它是**同一接口下的一个真实实现，只是确定性**——就像内存实现之于数据库、`Map` 之于存储引擎。它的确定性不是"为了方便测试而牺牲真实性"，而是它的设计目的：让阶段 1-6 的整条链路可复现、可离线、可断言。阶段 7 之后它也不会被删——那时它的价值从"唯一实现"变成"确定性参照物"，用来在生产适配器出问题时排除上游因素。

## 问题 4：为什么 `getDefaultStreamFn` 未安装时抛具名错误，而不是返回 `undefined` 让下游炸？

**一句话**：因为"忘记在组装根安装"是使用者最可能犯的错，而错误的**抛点决定了错误的可读性**。

具体对比。假设它返回 `undefined`：

```
TypeError: streamFn is not a function
    at agentLoop (packages/core/src/agent-loop.ts:21:24)
```

这行栈信息回答了"哪里炸了"，但没回答"我做错了什么"。看栈的人的思路会是：`agentLoop` 有问题？还是我用错了参数？`streamFn` 是可选参数，我明明没传——那它该有个默认值啊，默认值呢？

实际抛具名错误时：

```
Error: no default stream fn installed; call setDefaultStreamFn() at composition root
    at getDefaultStreamFn (packages/ai/src/stream-fn.ts:14:9)
    at agentLoop (packages/core/src/agent-loop.ts:21:24)
```

栈顶从"core 的内部实现细节"变成了"**插槽发现自己是空的**"，而消息里直接给出了修复动作（`call setDefaultStreamFn()`）和它的位置（`at composition root`）。四种信息一次给全：什么坏了、为什么坏了、怎么修、修在哪。

三处具体收益：

**(1) 抛点从下游移到源头。** `undefined` 一路传到 `for await (const e of undefined)` 才炸，此时栈上已经有了 `agentLoop` 的循环体——一个初学者会先去读循环，而循环是对的。具名错误在 `getDefaultStreamFn` 里就断了，栈上只有两个帧，两个都对。

**(2) 修复动作写在消息里。** 这条错误不需要任何文档或搜索：`call setDefaultStreamFn() at composition root` 就是**下一步的动作**。"返回 undefined 让下游炸"的错误消息无法包含修复动作——因为 `agentLoop` 不知道 `undefined` 意味着"没安装"还是"有人显式关了 provider"。

**(3) 它把"忘记组装"从一个静默可能变成一个响亮失败。** 这条和问题 2 的保证 (4) 是同一件事的两面：core 不认识任何 provider，所以它**没有能力**贴心地给一个默认值；它唯一能做的是响亮地报告插槽是空的。Pi 的原文同理——`agent-loop.ts` 对应的 `stream-fn.ts:17`：*"No default stream function configured. Pass streamFn explicitly or call setDefaultStreamFn()."* 两条出路都给出来了：要么显式传，要么在组装根装。

对照 spec 里那条贯穿全项目的错误原则：

> **模型能修的错误回喂模型；模型修不了的抛给人。**

这条错误属于后者：**它不是模型的错，是组装者的错，模型无从修起**。所以它必须抛给人，而且必须抛得让人能立刻动手。阶段 2 里会看到同一条原则的另一半——工具执行失败**不抛**，而是编码成 `isError: true` 的 toolResult 回喂模型，因为模型能修。

## 小结

四个问题问的是同一件事的四个切面：**依赖反转缝（seam）要缝在哪一层、用什么形状、边界怎么验。**

| 问题 | 决策 | 判据 |
|---|---|---|
| 1. 函数 vs 接口 | 函数类型 + 插槽 | 单方法、接收者不携带信息、需要内联 → 函数；需要被查表/携带身份 → 接口 |
| 2. core 不 import provider | 只依赖 `ai` 的类型 + 读插槽的 getter | `grep` 可验的边界，比口头承诺强 |
| 3. 假模型住 `ai/src/` | provider 层的合法实现 | 生产入口（`cli`）在用它；与阶段 7 的 `anthropic.ts` 同层 |
| 4. 未安装抛具名错误 | 抛在源头，消息含修复动作 | 组装者的错不可回喂模型，必须抛给人且能立刻动手 |
