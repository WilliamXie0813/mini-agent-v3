先建立全局地图

模型按顺序发出三个调用：c1 slow(100ms)、c2 fast(20ms)、c3 medium(30ms)。

源顺序：      c1 → c2 → c3
prepare：     c1 → c2 → c3       // 串行
execute：     c1 ───────── 100ms
             c2 ── 20ms          // 并行
             c3 ─── 30ms
end 事件：    c2 → c3 → c1       // 完成顺序
result 消息： c1 → c2 → c3       // 源顺序
核心

UI 与模型不是同一个消费者。UI 要实时完成顺序；模型要稳定协议顺序。阶段 6 不是“加 Promise.all”，而是同时维护这两种顺序。

3
两阶段并行：为什么 Promise.all 只能放在 prepare 之后

	

		
阶段一 · prepare 串行

		
for (const toolCall of toolCalls) {
  await emitToolStart(toolCall);
  const preparation = await prepareToolCall(...);

  if (preparation.kind === "immediate") {
    // invalid / block 现在就 finalize + end
    entries.push(finalized);
  } else {
    // 只保存 thunk，还不执行工具
    entries.push(async () => execute(preparation));
  }
}

		
permission hook 可能等待人类点击。串行 prepare 保证权限问题按模型顺序出现，并保证任何 execute 开始前，整个 batch 已完成 preflight。

	

	

		
阶段二 · execute 并行

		
const ordered = await Promise.all(
  entries.map(entry =>
    typeof entry === "function"
      ? entry()                  // thunk 并行运行
      : Promise.resolve(entry)   // immediate 占住源 index
  )
);

		
Promise.all 的执行完成时间可以乱序，但返回数组仍按输入 index 排列。这是后面恢复 source-ordered messages 的关键。

		
展开 parallel orchestrator 的完整核心结构
phase 1:
  start c1 → prepare c1 → store thunk #1
  start c2 → prepare c2 → store thunk #2
  start c3 → prepare c3 → store thunk #3

phase 2:
  Promise.all([thunk #1, thunk #2, thunk #3])

inside each thunk:
  execute → finalize → emit tool_execution_end

after Promise.all:
  for outcome of ordered:
    emit toolResult message_start/end

5
同文件 mutation queue：并行不是无条件同时写

	
工具层已经允许并行，但文件不是普通的独立任务。两个 edit 即使修改不同片段，也可能读取同一份旧快照，最后一个写入者会覆盖前一个结果。本章从这个完整失败现场开始，再逐层解释 queue 里的每个 Promise。


	
5.1 没有 queue：为什么会丢更新

	
初始文件是 alpha beta，两个 edit 同时开始：

	

		
Lost update · 两个工具都基于同一份旧内容计算

		

			
T1edit #1 read → "alpha beta"

			
T2edit #2 read → "alpha beta"

			
T3计算 → "ALPHA beta"

			
T4计算 → "alpha BETA"

			
T5write → "ALPHA beta"

			
T6write → "alpha BETA"（覆盖 #1）

		

		
最终文件是 alpha BETA：第一个 edit 的 ALPHA 丢失。

	

	
前端类比
类似两个异步任务都读取同一个旧 state，再分别 setState(update(oldState))。后一次更新没有基于前一次的新 state 计算，因此覆盖了前一次结果。文件没有 React 的函数式更新，需要显式异步互斥。


	
5.2 为什么不能只锁住 writeFile

	

		

			
错误边界：只锁 write

			
const before = await readFile(path);
const changed = edit(before);

await lock(() =>
  writeFile(path, changed)
);

			
两个调用在进入锁之前已经读到了相同旧内容。write 虽然没有同时发生，第二个仍会写回基于旧快照计算的结果。

		

		

			
正确边界：锁住完整事务

			
await withFileMutationQueue(path, async () => {
  const before = await readFile(path);
  validateUniqueOldText(before);
  const changed = edit(before);
  await writeFile(path, changed);
});

			
第二个 edit 只有在第一个完成后才重新读取文件，所以它读到的是 ALPHA beta，最终得到 ALPHA BETA。

5.4 tails Map 存的不是结果，而是“前一位什么时候结束”

	

		
Promise chain · 同一文件的三位排队者

		

			
Map key
/repo/a.txt（canonical realpath）

			
tail #1
edit #1 的完成信号 current #1

			
tail #2
tail #1.then(() => current #2)

			
tail #3
tail #2.then(() => current #3)

		

		
// edit #2 到来时，Map 中的 tail #1 就是它的 previous
const previous = tails.get(key) ?? Promise.resolve();

let release = () => {};
const current = new Promise(resolve => {
  release = resolve;
});

const tail = previous.then(() => current);
tails.set(key, tail);

await previous;  // 等前一位 release
try {
  return await operation();
} finally {
  release();      // 叫醒下一位
}

		
operation Promise 告诉当前调用方“成功还是失败”；queue Promise 只告诉下一位“前一个已经结束”。两个职责刻意分离。

	


	
5.5 为什么失败不会把后续队列一起毒死

	
即使 operation() throw，finally 仍会执行 release()。当前调用方拿到 rejection，但下一位等待的是独立的完成信号，它仍会正常被唤醒。

	

		
错误做法把 operation 自身的 rejected Promise 存进 Map；后续所有 await previous 都继承 rejection，队列永久中毒。

		
当前做法operation 的成功/失败返回给调用方；内部 current 只负责 resolve“我结束了”，后续任务继续。

	


	
5.6 为什么删除 Map 时要判断 tails.get(key) === tail

	
edit #1 运行期间，edit #2 可能已经把 Map 更新为 tail #2。若 #1 完成时无条件 delete(key)，会误删 #2 的队列；随后 edit #3 会以为没人排队，与 #2 并行。

	
finally {
  release();

  // 只有自己仍是最后一位，才说明后面真的没人
  if (tails.get(key) === tail) {
    tails.delete(key);
  }
}


	
5.7 registrationTail：防止异步 realpath 反转调用顺序

	
这里解决的是一个更隐蔽的竞态：函数调用顺序是 #1、#2，但 realpath() 的返回顺序可能是 #2、#1。如果谁先拿到 realpath 谁先注册 Map，后调用的 #2 就可能排到 #1 前面。

	

		
Realpath registration race · 切换观察有无 registrationTail

		

			

				
调用顺序固定

调用 edit #1（realpath 预计 80ms）

					
T1
调用 edit #2（realpath 预计 10ms）

// 每次调用一进入函数，就先在全局 registration queue 中占位
const waitForRegistration = registrationTail;

let releaseRegistration = () => {};
registrationTail = new Promise(resolve => {
  releaseRegistration = resolve;
});

await waitForRegistration;

try {
  const key = await realpath(path);
  const previous = tails.get(key) ?? Promise.resolve();
  const tail = previous.then(() => current);
  tails.set(key, tail);
} finally {
  releaseRegistration();
}

	
边界在哪里
registrationTail 只串行化 realpath + 查询旧 tail + 注册新 tail 这段很短的 preflight。注册完成后，文件 A 与文件 B 的真实 operation 仍然可以并行；只有相同 realpath 的 operation 才等待彼此。






	
6
降级与 Abort：并行不是永远更好

	

		
条件模式原因

		
Agent.toolExecution = sequential整批串行宿主明确要求可预测顺序

		
任一 ToolDef.executionMode = sequential整批串行避免半并行 batch

		
全部 parallel/未声明prepare 串行、execute 并行默认高吞吐

	

	

		
Abort 发生在 phase 1 与 phase 2 之间

		

			
已经 prepared 的 c1
thunk 启动时发现 signal.aborted → Operation aborted

			
尚未 prepare 的 c3
仍发 start/end，直接 synthetic aborted outcome

		

		
最终 toolResult 仍按 c1/c2/c3 源顺序进入历史，然后 Agent 追加 terminal aborted assistant。sequential 模式则不会为尚未开始的调用伪造 lifecycle。

	






	
7
回测：判断是否真的掌握双顺序

	

		
1. 为什么 prepare 不能 Promise.all？
prepare 包含权限 hook。并行会同时弹多个交互，并让顺序策略不可预测；所有 execute 也必须等 preflight 完成。

		
2. 为什么 end 与 message 不同序？
end 服务 UI 实时反馈，message 服务模型协议配对；两个消费者需要不同顺序。

		
3. 为什么 immediate outcome 也要占 index？
invalid/blocked 如果从 ordered entries 消失，后续 toolResult 会向前错位，无法与原 toolCall 一一对应。

		
4. 为什么一个 sequential 工具让整批降级？
否则会形成“这个工具串行、其他工具同时跑”的半并行状态，依赖和事件语义难以预测。

		
5. 为什么锁要包 read/validate/write？
只锁 write 时，两个 edit 已经基于相同旧内容计算，后写仍会覆盖先写。

		
6. 为什么 queue key 用 realpath？
相对路径、绝对路径和 symlink 可能指向同一个文件；字符串不同不代表资源不同。
